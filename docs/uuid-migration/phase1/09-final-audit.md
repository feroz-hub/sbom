# Phase 1 final UUID audit and implementation proposal

Audit date: 2026-10-16, Asia/Kolkata. Repository: `feroz-hub/sbom`; branch: `feat/native-user-management`; HEAD: `2f48ff835d9e692fc84b31aaa951aad2495888ac`. This is a consolidation of audits 01–08 against the audited working tree, including the existing frontend edits. No implementation, database access, migrations, application startup or load tests were performed for this consolidation. The existing changes and earlier audit files were preserved. Origin matched HEAD when audit 01 checked it; no new live-origin check is implied here.

## Decision

**GO for Phase 2 design, implementation and isolated validation under the approved hybrid architecture. NO-GO for production deployment or public cutover.** The source inventory is sufficient to plan the work, but the intended deployment database, ambiguous identifier namespaces, dynamic payload coverage, authorization regression evidence, performance baseline and rollback rehearsal remain release gates. This recommendation does not authorize implementation or database mutation in this audit task.

The approved architecture supersedes the full-PK replacement alternatives discussed in earlier audits: retain existing integer PKs/FKs and joins; add immutable random UUIDv4 public identifiers where needed; eliminate outward internal identifiers; preserve tenant and object-level authorization. Existing UUID-string PKs and natural/composite/hash keys are retained internally rather than forcibly converted to integer or replaced. UUIDv7 and full UUID PK/FK conversion are outside this proposal.

## Public identifier contract

1. Add a native PostgreSQL `uuid` column named `public_id` to an externally identified integer/hash-keyed resource. Generate random UUIDv4 on all application write paths; propose a database UUIDv4 default for direct inserts only after verifying the target PostgreSQL capability. Backfill once, persist permanently and enforce uniqueness/non-null after validation. Do not derive UUIDs from integer IDs or regenerate on reads. The proposed uniqueness scope is global per resource table, with a unique UUID index; a composite tenant/UUID index is optional only if measured plans justify it.
2. Public DTO fields such as `id`, `project_id`, `tenant_id`, `run_id`, `version_id` and `*_ids` contain UUIDv4 strings when they refer to local resources. Field spelling need not change. Resolve through resource-specific repositories using UUID plus authorized scope, then pass existing integers to services and joins. Cross-resource UUID equality never implies identity. Platform resources and nullable-tenant configuration require explicit platform permissions; user/account resources require account/membership rules. Provider models inherit credential scope.
3. Existing validation-session, repair-job and AI-batch UUID-string PKs are reused after stored-value/version checks. Keep their physical varchar/FK representation for Phase 2 unless separately justified. Reject caller overrides that violate UUIDv4/immutability. Invalid historical values are an evidence gap requiring an explicit remediation/alias design; never silently regenerate identifiers already issued.
4. Natural CVE keys, advisory IDs, bom-ref, PURL/CPE, package identities, provider names/codes, versions, hashes used as artifact integrity/provenance and external issuer/subject IDs retain their domain meaning. Internal cache storage keys are different: compare and AI cache identifiers currently exposed as handles/diagnostics will receive public UUID mappings. Secret tokens remain opaque secrets, not row identifiers or UUID replacements.
5. Authenticated, admin, legacy and separate-service public boundaries all count. Paths, queries, bodies, nested models, raw dictionaries, errors, validation errors, audit metadata, SSE/Redis-progress projections, cursors, JWT claims, files, filenames, links and email headers must satisfy the contract. Encoding or signing an integer does not conceal it. Unknown JSON shapes need explicit schemas/allowlists; broad numeric-to-UUID string replacement would corrupt domain data.

### Data and query plan

Keep the compact integer PK/FK indexes and joins. A boundary lookup uses the resource UUID together with authorized tenant/parent scope; after resolution, reuse the existing integer graph. A global per-table unique public UUID index is the default proposal; add tenant-leading/composite/covering indexes only when representative plans justify them. Retain separate scope predicates for tenantless/platform/account resources. Avoid per-row UUID resolution for nested arrays; project related public IDs through joins or fetch mapping batches once per resource type/page.

Backfill work must be bounded by stable internal integer ranges, restartable, collision-safe and observable without logging business records or secrets. A default on new inserts does not populate old rows. Future concurrency/write-lock budgets, index creation strategy, backup/PITR capability and transaction boundaries must be reviewed against the actual target. Physical native-UUID conversion of the existing varchar PKs is not a Phase 2 prerequisite.

## Rollback requirements

Before public cutover, the additive schema may remain unused while the current application is restored; retain completed UUID mappings for deterministic retry. Do not drop/recreate IDs, reseed sequences, rewrite PK/FK relationships or modify encrypted token AAD. Review compatibility of defaults/constraints with all writers before deploying them.

After public cutover, **rolling back to an integer-exposing API violates the approved architecture**. Provide a tested UUID-capable fallback release or disable the affected operation/fail closed with a maintenance response. Keep UUID columns, mappings and all mappings assigned to post-cutover rows; repeated requests and issued links must identify the same resource. Preserve integer storage and internal task payloads. Do not expose dual numeric/UUID responses or numeric compatibility endpoints as an emergency rollback.

Triggers include authorization/isolation failure, internal-ID leakage, missing/unstable mappings, broken history/artifact semantics or measured performance/operational budget breach. Pause cutover/backfill safely, preserve internal evidence and mappings, apply the UUID-aware fallback or disable affected traffic, then rerun scoped acceptance. A schema downgrade that drops public mappings requires a separate recovery design and is not the proposed rollback.
