## Decision summary and evidence boundaries

A public UUID can reduce straightforward sequential enumeration, but tenant and object-level authorization remain required. This repository already has substantial source-level enforcement; the migration must preserve it. This review does **not** establish that every endpoint is free of BOLA/IDOR, nor does public integer exposure alone establish an exploit. OWASP explicitly treats complex identifiers as defense in depth alongside per-object checks. [OWASP IDOR prevention](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html).

Compare two future architectures before choosing: retain internal integer PK/FK joins with public UUIDs at exposed boundaries, versus replacing internal PK/FK types with UUIDs. The first limits high-fan-out join churn but needs comprehensive outward ID translation and additional unique indexes; the second makes internal identity uniform but touches more indexes, validators, queue payloads, JSON and chronology assumptions. Neither is approved or implemented by this audit.

Evidence labels: **source verified** = observed query/control/declaration; **catalog snapshot** = metadata from audit 04’s earlier read-only local A/B snapshots; **risk/hypothesis** = needs an isolated future test. No latency, throughput, index-size, memory, query-count trace, EXPLAIN plan, cache-hit-rate or production-volume measurements were collected. Arithmetic derived from source or catalog counts is identified as such.

The catalog B snapshot is the closest local schema baseline: PostgreSQL 16.15, revision 079, 72 tables including Alembic, 72 PKs, 143 FKs and 512 indexes. A is an older, different local target at revision 055. B is not schema-identical to ORM and neither target is certified as the deployed application target. There are no native uuid columns in either snapshot; existing batch/session/repair UUID-shaped PKs use varchar(36). ## PK/FK indexes and catalog coverage

PostgreSQL creates indexes for primary/unique constraints, but does not automatically create an index on the referencing FK columns. A referenced-key index is not evidence of a child-side access path. [PostgreSQL 16 constraints](https://www.postgresql.org/docs/16/ddl-constraints.html). Leading-column order and predicates matter for a multicolumn B-tree; planner choice still depends on the query and statistics. [PostgreSQL 16 multicolumn indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html).

Recomputed **from the saved B catalog text**, not a new DB query: 115/143 FKs have a valid/ready, nonpartial simple B-tree with the FK tuple as an ordered leading prefix; one more has a permuted leading tuple; 27 have no complete match under that conservative rule. All 72 PK constraints are recorded in audit 04. The 27 are **review candidates**, not 27 missing indexes or proven slow queries: tenant-leading indexes, a shorter prefix, predicate-specific paths or other access methods can still help. The rule excludes INCLUDE-only columns and expression/non-B-tree indexes; no predicate implication or planner equivalence was executed.

Examples of existing paths: analysis_finding has (analysis_run_id), (component_id), (analysis_run_id,severity), (tenant_id,id) and unique (analysis_run_id,reconciliation_key); sbom_component has SBOM and tenant paths plus fingerprint uniqueness; ai_fix_batch has (run_id,status)/(tenant_id,id); VEX snapshots have (analysis_run_id,investigation_id), tenant and SBOM paths, but no unconditional leading investigation_id path in B. AuditLog has separate entity/target/tenant/time indexes. See the full constraint-by-constraint appendix below.

Some single-column id indexes duplicate a PK access key, for example analysis_finding and audit_log. Treat them as possible write/storage overhead to measure; do not drop any based on this audit. B index-name differences and the missing VEX superseded_by FK are already documented in audit 04. Retain partial predicate semantics, index validity and composite tenant constraints in comparisons.

Under a hybrid design, resolve resource UUID plus mandatory tenant into an internal id, retain internal joins, and explicitly translate outward references in one/batched queries. A globally unique public_id supports global lookup but still requires tenant predicates; a tenant-local unique (tenant_id,public_id) is sufficient only if every lookup supplies tenant and all dependent contracts accept that uniqueness model. Keep integer capacity planning separate. Under a full replacement, every FK/composite unique key, cache/list/sentinel, JSON join, worker validator and serializer must be updated; string-casting numeric IDs is not a UUID migration.

Native PostgreSQL uuid represents 128 bits; integer and bigint are 4 and 8 bytes. These are type storage characteristics, **not measured table/index size multipliers**: row headers, alignment, other keys, fan-out and index design change total cost. Compare native uuid with current varchar(36) separately. [PostgreSQL UUID type](https://www.postgresql.org/docs/16/datatype-uuid.html), [integer storage](https://www.postgresql.org/docs/16/datatype-numeric.html).

Benchmark random UUIDv4 and an explicitly chosen application-generated ordered UUID variant only if both are genuine design candidates. An ordered UUID may change insertion locality; UUIDv7 carries a timestamp and is not equivalent to opaque random identity. Do not promise a speedup or treat order as authorization. PostgreSQL 16 storage compatibility does not imply built-in UUIDv7 generation. [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html).
