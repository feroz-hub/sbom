## Self-reference and composite interpretation

- `sbom_source.parent_id`, `source_sbom_id` and `converted_sbom_id` all point to `sbom_source.id` with no explicit DB delete action; lineage and conversion are separate links. `sbom_component.duplicate_of_component_id` uses CASCADE. `vex_documents.superseded_by_id` uses SET NULL. These are the five self-FKs expanded in the declared matrix.
- `(tenant_user_id, tenant_id) → tenant_users.(id, tenant_id)` enforces same-tenant membership for role assignments, CASCADE ([app/models.py:503](../../../app/models.py#L503)).
- `logical_sbom.(product_id, tenant_id) → products.(id, tenant_id)` uses CASCADE ([app/models.py:747](../../../app/models.py#L747)), in addition to its individual product and inherited tenant FKs.
- `sbom_source.(logical_sbom_id, tenant_id)` and `(logical_sbom_id, tenant_id, product_id)` point to the corresponding logical_sbom tuples with unspecified actions ([app/models.py:843](../../../app/models.py#L843), [app/models.py:844](../../../app/models.py#L844)). Nullable product_id affects whether the triple constraint is checked under default composite MATCH SIMPLE semantics; the nonnullable logical/tenant pair is a separate constraint. Migration evidence: [alembic/versions/076_logical_sbom_versions.py:48](../../../alembic/versions/076_logical_sbom_versions.py#L48).
- Product → current SBOM → logical SBOM → product forms a cycle, alongside ordinary product ownership of SBOM versions. `Product.current_sbom` explicitly has post_update=True ([app/models.py:693](../../../app/models.py#L693)). Same-tenant scope must be assessed per constraint: a single FK to id does not by itself enforce that child and parent tenant_id match.

## Cascade, SET NULL and retention interpretation

The declared matrix is authoritative for **current model intent**. In particular:

- Identity/user deletion cascades credential, token, identity and membership rows where CASCADE is explicitly declared; assignment/history attribution often uses SET NULL, and role/history retention includes RESTRICT edges. The per-edge actions above must be preserved as separate contracts.
- The inherited tenant FK does **not** declare CASCADE. Explicit tenant FKs on configuration, assignment and recommendation policy models can declare CASCADE; role assignment history uses RESTRICT; authorization/credential audit attribution uses SET NULL. Tenant ownership is not one uniform delete policy.
- SET NULL clears only the constrained column(s), not JSON or namespaced copies of that identifier. Examples include product current_sbom_id, VEX component/statement/run pointers, audit actor/target FKs and recommendation source project/product/SBOM/component pointers.
- ORM delete-orphan is explicit for authorization mappings, validation session events, VEX document statements, remediation history and recommendation candidates/checks/factors (see ORM matrix). Other navigation defaults must not be described as delete cascades.
- `SoftDeleteService` updates is_active/deactivation attribution, follows eligible downward ORM relationships, stops at excluded/non-soft-delete models, and separately removes comparison caches ([app/services/soft_delete.py:48](../../../app/services/soft_delete.py#L48), line 138, line 171). It does not execute database ON DELETE semantics for soft-deleted rows.
- Permanent SBOM deletion uses explicit service ordering and cleanup, including current SBOM nulling, repair/workspace children, comparison/run caches and self-reference nulling ([app/services/sbom_delete_service.py:354](../../../app/services/sbom_delete_service.py#L354), lines 366, 403, 410, 428, 442, 452, 462). It inspects unknown FK dependencies ([app/services/sbom_delete_service.py:564](../../../app/services/sbom_delete_service.py#L564)). This is source-observed service behavior, not proof every possible dynamic dependency is handled.
- Policy versions and recommendation events are protected by ORM before_flush guards ([app/models.py:2754](../../../app/models.py#L2754)); VEX snapshots have a separate guard at [app/models.py:2801](../../../app/models.py#L2801). Such guards do not establish DB-level immutability or execute for every bulk/DB-side action. The unconstrained historical candidate ID is intentional, not a missing-FK conclusion based only on naming.
