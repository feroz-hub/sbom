## Proposed per-table schema

Common specification **U** for every row below:

- Add a non-PK `public_id` of native PostgreSQL `uuid` type. Expand nullable with no ADD COLUMN default, then set its insert default to **`pg_catalog.gen_random_uuid()`** separately within the same short transaction; install the proposed identity guard before committing. This separation avoids specifying a volatile expression as an ADD COLUMN default. Existing rows remain NULL until backfill.
- Database generation is authoritative for omitted values, including old ORM writers and direct SQL. An INSERT guard additionally assigns UUIDv4 when `NEW.public_id IS NULL`, covering explicit NULL inputs; valid supplied UUIDv4 is allowed for controlled import/restore, never as client-chosen API identity. The public API's rejection of a client `id`/`public_id` remains W0.2 boundary work.
- A row-local version/variant CHECK permits NULL during expand but rejects non-v4 values. A unique full B-tree on `public_id` with default NULLS DISTINCT semantics permits multiple legacy NULLs. Finalize with validated checks, `NOT NULL`, and a nondeferrable per-table UNIQUE constraint backed by that same index. Do not add a second UUID index or a UUID PK.
- A database UPDATE guard permits only the first NULL → valid UUIDv4 assignment, identical-value assignments and unrelated updates. Once non-NULL, changing it or setting it to NULL fails. Ordinary in-place updates preserve it; actual newly created records receive new UUIDs. No update-time default or automatic UUID regeneration.

PostgreSQL 16 documents core `gen_random_uuid()` as a v4 generator; this design requires no new uuid-ossp/pgcrypto extension. Availability, function resolution/execute rights and approved target version must still be verified on D. Native `uuid` accepts versions beyond v4, so type alone is insufficient. [PG16 UUID functions](https://www.postgresql.org/docs/16/functions-uuid.html), [PG16 UUID type](https://www.postgresql.org/docs/16/datatype-uuid.html).

### UUID validity and immutability behavior

Proposed v4 CHECK expression, documented here only (not executed):

```text
public_id IS NULL OR public_id::text ~
  '^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$'
```

PostgreSQL canonical UUID text makes this a row-local version/variant check; `NOT NULL` is a separate final invariant. The database CHECK does not enforce W0.2's stricter incoming wire grammar: alternate textual UUID spellings may already be canonicalized by a database cast. Future API validation remains necessary. UNIQUE treats NULLs as distinct by default; do not use NULLS NOT DISTINCT during nullable expand. [PG16 constraints](https://www.postgresql.org/docs/16/ddl-constraints.html).

Proposed BEFORE INSERT allocator and AFTER UPDATE immutability validator, both FOR EACH ROW, with this shared function contract:

| Old/new state | Guard behavior |
| --- | --- |
| INSERT without UUID or explicit NULL | Assign `pg_catalog.gen_random_uuid()` to NEW.public_id; do not touch any other NEW field. Default normally handles omitted values; guard covers explicit NULL. |
| INSERT with supplied UUID | Leave value unchanged; CHECK enforces v4/variant and unique index enforces current-row uniqueness. Controlled restore can retain an existing issued mapping. Normal API create must not accept supplied identity. |
| UPDATE old non-NULL; new IS DISTINCT FROM old | Reject with stable generic integrity error; do not include UUIDs, row values or SQL text in public errors. Covers NULL and UPDATE SET public_id=DEFAULT as reassignment. |
| UPDATE old NULL; new valid non-NULL | Permit first persistent assignment. Backfill is the authorized caller; invalid type/version fails. |
| UPDATE old NULL; new NULL | Permit ordinary legacy-row updates during expand. No automatic assignment on unrelated UPDATE; final nullability enforcement ends this transitional case. |
| UPDATE old/new same non-NULL | Permit. Domain updates never rotate identity. |

Use a normal invoker function, schema-qualified core calls and a hardened `search_path` (pg_catalog); it must not query business tables, write audit rows or alter timestamps. INSERT returns NEW after allocation. The UPDATE branch validates final NEW against OLD and raises on reassignment; its AFTER-trigger return value is ignored. Run it for all UPDATEs, not merely a statement's UPDATE OF public_id list: other BEFORE triggers can alter NEW. AFTER validation avoids relying on those triggers running before a BEFORE UPDATE identity check. Inventory trigger ordering and column grants on D; fail readiness if any existing trigger changes unrelated columns during the backfill or rewrites/nullifies public_id after INSERT allocation. Do not disable business triggers to bypass the check. Runtime roles must not be able to disable triggers, alter constraints/functions or use replication bypass. DDL owner/superuser can bypass safeguards; that trust boundary remains explicit. [PG16 trigger behavior](https://www.postgresql.org/docs/16/sql-createtrigger.html).

Immutability and UNIQUE protect assigned identities of extant rows; they do not alone prevent privileged DELETE/reinsert or deliberate reuse of a hard-deleted row's UUID. Ordinary allocation always generates a fresh UUID. Historical non-reuse/tombstone and privileged restore policies remain later acceptance dependencies; no seventh registry table or deletion-policy change is introduced here. Do not promise an absolute all-history database reuse guarantee from a six-table UNIQUE index.

### Why staged defaults and constraints

PG16 avoids a rewrite when adding a column without a default; a volatile ADD COLUMN default rewrites existing rows. SET DEFAULT applies to subsequent operations without filling old rows. `VALIDATE CONSTRAINT` uses SHARE UPDATE EXCLUSIVE; a validated non-null CHECK can avoid the verification scan during SET NOT NULL. Keep that CHECK until the later command. Attaching an eligible prebuilt index avoids building a second index. These are reasons for the sequence above, not claims of zero locking. [PG16 ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html).

### Concurrent inserts, backfill batches and reruns

The column, default and trigger become visible together when each S1 transaction commits. DDL lock acquisition waits for conflicting writers; enforce a bounded lock budget rather than permitting a long wait queue. Once S1 commits, legacy inserts omitting the column and explicit-NULL inserts receive UUIDs. Old rows updated for unrelated business reasons may remain NULL until S3; the nullable v4 check allows that. S5 requires no NULLs regardless of row status. Existing prepared statements/import shapes must be included in compatibility tests.

Proposed S3 algorithm (design pseudocode, not a script to run):

```text
For each approved table, retain a captured integer high-water id H.
Start checkpoint before the minimum existing key (no positive-id assumption).
For each transaction:
  Select at most N NULL-public_id rows in checkpoint < id <= H order by id,
  locking the selected rows; do not fetch raw documents or business payloads.
  UPDATE only those rows, rechecking public_id IS NULL,
    SET public_id = pg_catalog.gen_random_uuid().
  RETURN only the bounded internal keys needed for private progress tracking.
  Commit; then advance checkpoint. Persist private progress outside business rows.
If no rows selected, finish this pass, not the entire validation phase.
Repeat a NULL catch-up sweep over all key ranges, including <= checkpoint and > H.
Do not finalize until the validated nn CHECK proves completeness.
```

Use direct PostgreSQL UPDATE/SQLAlchemy Core with explicitly enumerated table/column SQL, not ORM object flushes. The SET list contains public_id only. No timestamps/row-version/status/tenant/ownership changes or model event dispatch. The maintenance connection is a separately authorized migration scope; do not disable tenant/session checks for ordinary application traffic. Backfill across all tenants is schema maintenance, never a new application access path.

Initial **proposed**, unmeasured rehearsal tuning: one worker, 500 rows per transaction, configurable 100–5,000 after observing row width/WAL/lock pressure; row-lock timeout 1s, statement timeout 10s and short between-batch throttling controlled by the operator. These are trial limits, not throughput/latency budgets or guaranteed safe production settings. Roll back a timed-out/deadlocked batch, back off and retry the same window; do not advance the checkpoint on failure. Wide source documents/component rows may require smaller batches. Bound table/window scans through existing integer PKs; no OFFSET paging, full-table payload load, single UPDATE of all NULLs or super-sized transaction.

Default plan does **not** use SKIP LOCKED, avoiding missed rows from a high-water checkpoint advancing beyond locked gaps. If parallelism/SKIP LOCKED is approved later, final gap rescans and locked-row reconciliation are mandatory; empty selection is not completion. PG16 explicitly describes SKIP LOCKED as yielding an inconsistent view. [PG16 SELECT](https://www.postgresql.org/docs/16/sql-select.html).

Transactions serialize competing assignments through row locks; `WHERE public_id IS NULL` makes committed mappings the source of truth. On connection loss/unknown COMMIT outcome, reconnect, inspect row/checkpoint state and retry NULL-only; never overwrite a value because progress logging was lost. A rolled-back tentative UUID may be regenerated because it was never committed or exposed. A committed UUID must remain unchanged. Lost checkpoint can restart at the beginning safely; explicit low-PK inserts and old transactions are covered by the final catch-up/check, not only MAX(id).

With S2 valid unique indexes, a duplicate aborts the batch. Investigate constraint/generator/import cause. A genuine collision on an uncommitted candidate can retry the NULL-only batch with fresh generation; do not rewrite existing winner rows or blanket-catch all IntegrityErrors as UUID collisions. For insert transaction retries, no response/link may issue before COMMIT; resource creation idempotency remains the service's responsibility, not guaranteed by a UUID default.

## Index builds, transaction boundaries and locks

Necessary UUID access paths: **six full unique B-tree indexes, one per table**. Default NULLS DISTINCT is intentional during expand. No partial `WHERE public_id IS NOT NULL` index: final UNIQUE USING INDEX should attach a full plain-column eligible B-tree. No tenant/public_id duplicate index, INCLUDE(id), UUID FK index or old-index removal is required by this baseline proposal. Tenant predicates remain necessary even when UUID is unique per table; plan-driven extra indexes are a separate proposal.

`CREATE UNIQUE INDEX CONCURRENTLY` must run outside a transaction block. It performs multiple phases, can wait on transactions/snapshots and can leave an invalid index on failure; unique enforcement may already affect writes before the build completes. Only one concurrent build per table is allowed. Do not treat the command as lock-free or assume the same-name object is valid. [PG16 CREATE INDEX](https://www.postgresql.org/docs/16/sql-createindex.html).

Alembic implementation proposal: isolate each concurrent operation in a small dedicated revision using `op.get_context().autocommit_block()`, with pre/post catalog verification and idempotent state handling. That block commits preceding work; it cannot make E/I/F one atomic migration. The current [env.py:48](/Users/ferozebasha/sbom/alembic/env.py:48) uses an outer transaction without explicit transaction_per_migration. A later reviewed integration must adopt short per-revision transaction boundaries or an equivalent explicitly isolated invocation; never silently alter configuration in this task. The repository pins [Alembic 1.18.5](/Users/ferozebasha/sbom/requirements.txt:1); validate these documented APIs against that pinned version in the future D rehearsal (the online API documentation currently describes a newer release). [Alembic autocommit documentation](https://alembic.sqlalchemy.org/en/latest/api/runtime.html#alembic.runtime.migration.MigrationContext.autocommit_block).

| Operation | Lock / operational design |
| --- | --- |
| Expand / SET DEFAULT / CHECK add / enforce | Plan short ACCESS EXCLUSIVE DDL transactions; acquire table in the fixed order and commit per table. No data batch or slow index build while holding this lock. |
| Guard creation | CREATE TRIGGER takes SHARE ROW EXCLUSIVE; when in S1 the stricter ALTER TABLE lock governs. Function creation must be reviewed and versioned, not replace unrelated functions. |
| Ordinary index build alternative | Takes SHARE, blocking normal writes; only consider for an empty/quiesced disposable fixture target with approval. It is not the assumed concurrent-insert rehearsal path. |
| Concurrent index / CHECK validation | SHARE UPDATE EXCLUSIVE operations can conflict with each other/maintenance even while ordinary DML continues. Schedule separately per table; inspect long transactions and approved progress metadata; do not kill blockers automatically. |
| Backfill | UPDATE/row locks plus normal DML locks; bounded transactions, retries and explicit timeouts. No exclusive whole-table data lock. |
| Attach UNIQUE / SET NOT NULL | Brief exclusive lock still required; valid nn proof and existing index reduce work, not the lock requirement. Perform postconditions before recording stage success. |

Lock classifications/conflicts and lock lifetime are documented in [PG16 explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html). Proposed DDL lock_timeout is 1s with bounded retry/backoff, and short metadata-only DDL statement_timeout 10s. Validation/concurrent-build timeouts must be separately set from observed synthetic scale and approved resource windows; leaving them infinite is not the proposal, and reusing the 10s metadata limit for a large build is not assumed appropriate. Set/reset session timeouts on autocommit connections; SET LOCAL does not survive transaction boundaries there. Failed preflight/build/lock acquisition stops the stage without broad retries or changing live service configuration.

Track pg_index validity/readiness, exact definition, constraint attachment and relevant progress/lock metadata before declaring index readiness. A valid standalone index is legitimate I-stage state even if the Alembic revision-marker update failed afterwards. For invalid remnants, stop backfill on that table, inspect before any approved drop/rebuild or reindex; account for continued uniqueness effects. Never DROP CONSTRAINT/CASCADE to clean a guessed index. Blind IF NOT EXISTS is insufficient. [PG16 index progress reporting](https://www.postgresql.org/docs/16/progress-reporting.html#CREATE-INDEX-PROGRESS-REPORTING).

If D has partitions/inheritance or advanced schema features unlike the assumed ordinary B-shaped tables, stop and revise the design. Do not apply the concurrent-parent-index plan to a partitioned table or add unsupported assumptions to a target discovered later.

## Storage, write overhead and future measurements

This is an additive two-identifier design, not a space saving. The existing 4-byte integer key remains and the UUID adds 128 bits/16 bytes of identifier payload per mapped row, before heap alignment/null bitmap/tuple overhead. UUID index entries also carry index overhead and row-location data; relation growth cannot be estimated as only 16 × row count. Existing FK payloads retain integer widths. [PG16 numeric sizes](https://www.postgresql.org/docs/16/datatype-numeric.html), [PG16 UUID type](https://www.postgresql.org/docs/16/datatype-uuid.html).

Expected cost categories to measure, not results: six additional unique-index structures; v4 generation, row-trigger/CHECK and uniqueness probes on inserts; random UUID index locality/page splits; buffers/WAL and temporary disk during concurrent builds; non-HOT backfill, dead tuples and maintenance on wide/high-index-count component/source tables. No table/index fillfactor change, index removal, UUIDv7 substitution or VACUUM FULL is proposed. Building uniqueness before backfill prioritizes early collision enforcement at a write cost; reversing that order would need a separately reviewed collision/exposure plan.

## Partial failure, forward recovery and rollback

| Observed future failure state | Recovery design |
| --- | --- |
| S1 transaction fails | Transactional DDL rolls back that table's unit; inspect actual catalog before retry. Shared function may already exist from a prior committed unit; verify exact signature/body/version rather than blindly replacing it. |
| S1 committed, I revision incomplete | Column/default/guard remain and protect new rows. Verify real index state and marker; build/recover only the missing/mismatched stage. Do not drop column or clear newly generated mappings. |
| Concurrent build fails / valid build but lost revision update | Invalid-index recovery requires explicit approved operation after catalog review; valid matching index is reused, then revision can complete normally. Do not stamp head to bypass a failed postcondition or drop a valid uniqueness constraint. |
| S3 partial/unknown commit | Rollback uncommitted batch where possible, reconnect and NULL-only retry; re-read stable committed mappings. Checkpoint can be behind; it must never be used to justify overwriting a UUID. |
| Validate/enforce fails | Keep expanded schema, default/guard/index and completed mappings; investigate NULL/wrong-version/side-effect cause. Retry independent validation/enforcement after correction approval. Never regenerate issued IDs to make validation pass. |
| App release rolled back before public issuance | Prefer leaving additive schema in place. Old explicit-column ORM inserts still work with defaults/guards; inventory/reflected/SELECT * tools require their own compatibility review. Disabling future UUID exposure is separate from deleting mappings. |
| Public UUID already issued | Keep all UUID columns/mappings and post-cutover mappings, constraints/defaults needed by writers and backups. Only roll back to a UUID-capable public application or fail closed/disable affected operation. Old integer-exposing endpoints are not an acceptable public fallback. |
| Proposed schema downgrade drops public_id or restore loses mappings | **Refuse automatically.** A historical pre-UUID backup cannot recover issued random mappings unless preserved/restored through an approved consistent recovery plan. Dropping/recreating UUIDs, deterministic regeneration, sequence resets and rekeying are not rollback strategies. |

Proposed Alembic downgrade behavior for the UUID addition chain is **fail closed with an actionable mapping-preservation message**, not silently remove columns/triggers/indexes. A truly disposable, unissued synthetic environment may be discarded/recreated only in a separately approved destructive test task; its disposability is not a generic safe-down permission for any database. Future release bookkeeping must record whether public identifiers have been issued; absence of a flag alone is not proof none escaped.

Backups and any private identity manifests must retain exact mappings for existing and post-cutover rows with consistent restore points; do not print/export business identifiers or secrets in audit output. Keep internal FK graph and task formats intact. Restoring the same record preserves its mapping; cloning a business record as a new version/occurrence must allocate a fresh one. Historical hard-deletion/non-reuse and mapping tombstones remain an explicit dependency before full public cutover.
